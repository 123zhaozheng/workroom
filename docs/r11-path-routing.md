# 第 11 轮 · R5：按路径前缀把文件路由到持久目录（借鉴 deepagents 的 CompositeBackend），执行层仍是单一入口

思路来自 deepagents：文件读写按路径前缀路由到不同的后端（`/memories/` 持久化），而 `execute` 永远走同一个默认后端。这里的对应关系：

| 路径（工作目录内） | 落在哪 | 谁能用 | 生命周期 |
|---|---|---|---|
| `memories/…` | 宿主机上**每个用户一个**目录（同一组织内） | 只有这位用户，且只在“能写这个会话”的会话里；分享的查看者、其他成员、其他组织永远看不到 | 永久（不随会话过期、不进版本历史） |
| `project/…` | 宿主机上**每个容器项目一个**目录 | 会话属于容器项目时才存在；项目所有者可读写，持有该项目**只读分享**的成员只读；其他人没有 | 永久 |
| 其余所有路径 | 会话工作区（和以前完全一样） | 和以前一样（空间 ACL） | 空闲 72 小时回收规则不变，版本历史照旧 |

执行层不变：沙箱里只有**一棵树**（`/work` 或远端的工作目录），`memories/` 与 `project/` 就是这棵树里的两个子目录。模型的文件工具、`code_run` 的输入输出、`sandbox_publish`、工作面板的文件 API 都用同一个路径写法。

和已有的 DB 记忆（`server/src/knowledge/memory.ts`）**无关，也没有合并**：那个是被检索后注入提示词的文本条目；这里是真正的文件，模型用文件工具和命令读写，想读多少读多少。

## 代码

- `server/src/tools/sandbox/stores.ts`：**唯一的路由函数** `WorkspaceStores.route(principal, space, conversationId, rel, workdir, {forWrite})` → `{ store: "conversation" | "memories" | "project", root, rel, writable, prefix }`，以及 ACL（`access`）、目录位置、配额（`checkQuota`、`mounts`）。`Sandbox.route(...)` 是它的入口。
- `Sandbox` 的 `workspace / entries / preview / readFile / writeFile / mkdir / remove / move` 全部经由它（新增末尾可选参数 `who?: Principal`）；HTTP 路由（`sandbox-routes.ts`，含发布）、沙箱文件工具（`sandbox-tools.ts`）、`code_run`（`localexec/service.ts` 的输入读取与输出文件写入）、后台任务输出发布（`jobs.ts`）都传入当前主体。**不传主体**（内部调用，例如技能脚本写 `.skill-run/…`）时只能到达会话工作区：以 `memories/`、`project/` 开头的路径会被拒绝，**绝不会静默写进会话目录**。
- 本机驱动：`DriverRunSpec.stores`；`namespaces` 与 `docker` 把两个目录绑定挂载到 `/work/memories`、`/work/project`（项目目录只读、或目录超过上限时内核级只读）。docker 对容器用户做 chown（与工作区一样）。
- 远端驱动：`remote-driver.ts` 的同步由“一个目录”改为“最多三棵树”（会话工作区 + 两个持久目录），各有自己的清单切片（键 `memories/…`、`project/…`，归属标记 `@store:<name>`；`:` 不可能出现在文件名里，不会冲突）。上传时三棵树一起上传；下载时远端 `memories/…` 的变化写回 **memories 的宿主机目录**，不写会话目录。
- `persist.ts`：版本快照遍历**跳过顶层的 `memories`、`project`**（也包括会话在本功能出现前自己建过的同名文件夹）。
- `prompt.ts`：沙箱段落里一两句话——`memories/` 永久保存并在这位用户的所有会话里可见；`project/`（仅当存在时）是本项目所有会话共享的目录。纯函数，提示词缓存照旧有效。
- `shared/sandbox.ts`、`shared/files.ts`：`expiresAt` 变为可选（持久目录里的文件不过期）。
- 界面：工作面板的文件列表本来就是树；两个文件夹就在列表里像普通文件夹（`memories`、`project`），没有改前端、没有额外文案。删除/改名这两个文件夹本身会得到明确的中文错误（只能操作里面的文件）。

## 存放位置与备份

`<dataDir>/orgs/<orgId>/stores/memories/<userId>/…` 与 `<dataDir>/orgs/<orgId>/stores/project/<projectId>/…`。在 `orgs/` 下面，所以数据目录备份**会包含**它们（备份只默认跳过每个会话的 `sandbox` 工作副本）。都是普通目录，**不是符号链接**（`workspace.ts` 拒绝符号链接逃逸，路由到的每个目录同样走那套检查）。

## ACL 矩阵（`Sandbox.route`，每次操作都按当前状态重新判断）

| 主体 | `memories/` | `project/`（会话在容器项目里） | `project/`（会话不在项目里） |
|---|---|---|---|
| 会话所在个人空间的所有者 | 读写（自己的目录） | 读写 | 404 `no_project_store`：“这个会话不属于任何项目…” |
| 旧版项目空间的非查看者成员（editor 等） | 读写（**各自**的目录） | 无（旧版项目没有 project/） | 同左 |
| 旧版项目空间的查看者 | 403 `store_forbidden` | — | — |
| 容器项目的只读分享对象 | 403 | 只读；写入/删除/移动/建目录 403 `project_readonly` | 404 |
| 同组织其他成员（无分享） | 403 | 404 | 404 |
| 其他组织 | 403 | 404 | 404 |
| 没有主体（内部调用） | 403 | 404 | 404 |

撤销分享或把会话移出项目后，`project/` 立即对对方/该会话消失（项目里的文件保留）。HTTP 层的空间 ACL 在此之前仍然生效（分享对象在 HTTP 上本来就进不了所有者的空间文件接口：403）。移动单个文件可以跨三个位置（先拷贝到目的地、检查目的地的配额与权限，再删除源）；跨位置移动文件夹被拒绝（400 `cross_store_folder`）。

## 配额

每个持久目录各有**单独上限**，默认**沿用工作区配额设置**（`WORKROOM_SANDBOX_QUOTA_MB`，默认 512 MB）；要单独设置用 `WORKROOM_SANDBOX_STORE_QUOTA_MB`（调用时读取）。会话工作区的空间配额不把它们算进去（不同的目录）。

- 通过 API/工具写入：超出返回 507 `store_quota`，例如“记忆目录（memories/）已满：已用 512 MB，上限 512 MB；请先删除不需要的文件”；覆盖同一文件只计差值。单文件上限 64 MB 与会话一致。
- 本机驱动运行前发现已超上限：该目录**以只读方式挂载**，运行输出附一行说明（“…已用 … 超过上限 …：本次以只读方式提供，请先清理再写入”），命令本身照常运行。运行**过程中**写满无法在内核层拦截（和会话工作区一样，只在运行前检查）。
- 远端驱动：同步回来的文件超出剩余额度时不保存，运行输出里逐个说明（“记忆目录（memories/）已满（上限 …），未保存：memories/x”）。

## 远端沙箱与并发写：不静默丢数据

- 一个远端沙箱可能被多个成员先后使用（团队空间的同一个会话）。归属标记 `@store:memories` 记录该文件夹是为谁/什么权限（`memories:<userId>`、`project:<id>:rw|ro`）上传的；换人或权限变化时**先清空该文件夹再重新上传**，所以 B 永远看不到 A 的 `memories/`。本次运行没有某个持久目录（没有权限、会话不在项目里）时，沙箱里对应的文件夹会被删除，在其中写的文件不保存并在运行输出里说明。
- 只读的 `project/`：上传后设为只读（chmod；单用户沙箱的提供方里用户仍可写，同技能目录的已知局限），**不会同步回宿主机**；沙箱里对它的修改在运行输出里说明条数。
- **冲突**：同一个持久目录文件被两个会话同时改（例如两个会话各自的沙箱同时在改 `project/plan.md`）。同步回来时若发现宿主机上的副本在这个沙箱上次同步之后已被别处改过，则**两边都保留**：先到的版本留在原文件名，后到的沙箱版本另存为同目录下 `<名>.conflict-<YYYYMMDD>-<HHMMSS>[-n]<扩展名>`（同一秒多次冲突自动加序号，绝不覆盖），运行输出说明（“project/plan.md 在别处（另一个会话）也被修改过：这次沙箱里的版本另存为 project/plan.conflict-…md，原文件保留的是另一处的版本；请对比后自行合并”）。冲突副本是普通文件，下次运行一起上传。宿主机上的检查与写入在同一个同步步骤里完成（单进程内没有间隙）。
- 会话工作区本身的语义没有变：宿主机副本优先并在运行输出里说明（那是会话私有的，没有“另一个会话”）。
- 远端删除：在沙箱里删除一个已同步过的持久文件，且宿主机副本没有变化时，宿主机上的文件也被删除（普通同步语义）；宿主机副本已被别处改过则保留。

## 版本历史

会话的版本快照（`persist.ts`）不包含这两个目录（它们不属于会话）；恢复旧版本也不会改动它们。本功能出现前，某个会话自己建过的 `memories/` 或 `project/` 文件夹里的文件：留在磁盘上的会话目录里，但被持久目录遮盖（列表看不到、运行时看不到、不再进入版本快照），每次运行的输出里会提示一次。会话工作副本被回收（72 小时）时这些遗留文件随会话目录一起被回收——这是本轮**没有迁移**的已知局限。

## 测试

`server/test/r11-path-routing.test.ts`（14 项，其中 LIVE 1 项在设置 `WORKROOM_TEST_OPENSANDBOX_URL/KEY` 时运行）：路由与 ACL 矩阵（所有者、只读分享、其他成员、其他组织、无主体、撤销分享、移出项目）；旧版项目空间；两个会话间的持久化与项目共享、项目外会话没有 `project/`、HTTP 上的 mkdir/移动/删除/发布；版本快照不含两个目录（含遗留同名文件夹）；备份包含持久目录；配额错误与“已满则只读挂载 + 说明”；沙箱提示词；文件工具；**本机 namespaces 驱动**与**真实 Docker 驱动**里 `cat` 到文件、写入落在存储而不是会话目录、满了之后内核只读；远端假提供方的上传/下载/换人清空/撤销清空/只读/上限/冲突副本；**真实 OpenSandbox**：一个会话写 `memories/`、`project/`，另一个会话读到，项目外会话没有 `project/`，宿主机并发编辑产生冲突副本。

## 没有做 / 未验证

- 常驻服务（`startService`：MCP stdio、技能服务）的沙箱里**没有**这两个目录（只有会话工作区）；它们是会话进程，不走文件路由。
- 子代理（subagent）的子会话没有目录库行，`project/` 不出现（`memories/` 仍按用户出现）。
- E2B、Daytona 的同步路径与 OpenSandbox 共用 `remote-driver.ts` 的逻辑，**没有**在这两家真实服务上联调。
- 删除用户/项目时其持久目录不会被自动清理（目录保留，没有人能访问；项目归档/删除后 `project/` 同样不可达）。没有按目录的 GC。
- 没有存储用量的界面展示（只有配额错误和运行说明）；没有前端改动。
- 同一远端沙箱里换人时，上一位在**最后一次同步失败**的情况下未写回的修改会随清空丢失（正常运行结束时已经写回）。
