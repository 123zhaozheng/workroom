# 第 13 轮：内核审查问题修复（基准 `ca22e85`，pi-durable 1.5.0）

外部审查复现了 6 个问题，另外指出 1 个事务窗口。结论是继续用 pi-durable，但执行身份、权限范围和恢复机制要先修。

处理方式：每一项先写出能复现审查结论的测试，在修复前的代码上确认失败，修复后再确认通过；然后跑全量回归。

第 1–3 项由主代理完成，第 4–7 项由 3 个子代理分别在独立的 git worktree 中完成。主代理合并后逐项审阅，并修正了合并带出的问题：
- 子代理误提交的 `node_modules` 链接；
- 空闲时压缩没有执行身份，被新的拒绝规则挡住。

## 1. 执行身份（P1）

**问题**：`continue` 和 `regenerate` 提交的运行没有新的用户输入，身份解析会回退到“最新一条消息的作者”。编辑者点“重新生成”时，用的是原作者的模型和工具权限。

**修复**（`server/src/runtime/service.ts`、`docs.ts`）：

- 新文档 `wr.run-actor`（`RunActorDoc`）按提交 id 记录操作人：`{userId, orgId, via, at}`，`via` 取值为 input / continue / regenerate / steer。它和提交写在同一个 pi-durable 事务里，所有入口都走 `#submitAs`：发送、继续、重新生成、立即发送。
- 运行的执行身份由 `actorOfRun()` 决定，按以下顺序：
  1. 本次运行中最新放入的输入：先查记录的操作人，再查条目上的作者；
  2. 运行没有放入任何输入时（继续或重新生成的运行，或已回答、正在收尾的运行）：本会话最近一个已不在排队中的提交的操作人；
  3. 子代理会话：沿所属父会话向上解析。
- 以上都解析不到时返回 null，调用方拒绝执行。“最新一条消息的作者”不再参与身份判断，只用于取附件和知识引用等数据。
- 模型、工具、知识库、凭据统一使用这份身份：`actorForTool`、`promptScope`、gateway 链接都经由 `principalOfRun` / `principalForRequest`。

**测试**：`server/test/r13-identity.test.ts` 第 1 项。
- 管理员在共享项目里用只有自己能用的模型；编辑者点“重新生成”，被拒（`model_not_allowed`），上游没有收到任何请求；编辑者点“继续”也一样。管理员自己重新生成正常。
- 修复前同一个测试中，编辑者能拿到受限模型的回答。

## 2. 备用模型的权限（P1）

**问题**：只在入口检查主模型，备用模型带 `wrNoFailover` 调用时跳过了检查；身份解析失败时直接放行。

**修复**（`server/src/ops/gateway.ts`、`ops/module.ts`）：

- 组装备用链时，对每个候选模型逐一检查当前执行身份能否使用，在取凭据、发请求之前完成。不允许的候选不调用，在路由记录里留一条 `skipped`，并写明原因。
- 每次调用都会检查权限，包括备用模型自身的内层调用。`wrNoFailover` 只负责防止递归和重复记账，不再影响权限检查。
- 运行时管理的会话存储（带 `wr.space` 文档）里，身份解析不出来或出错时，请求被拒绝：“无法确认这次运行代表哪位用户（执行身份缺失）”。
- 上下文压缩请求也挂上同一身份（`CompactionTask.beforeCompact`）。会话空闲时的压缩没有当前运行，改用最近一次记录的操作人。产品中的自动压缩发生在运行中，用的是运行身份。
- 没有 `wr.space` 文档的 Harness 不是用户会话，例如测试或内部用的独立存储，不要求执行身份。

**测试**：`r13-identity` 第 2 项。
- 成员遇到主模型 503 时，受限的备用模型收到 0 个请求，路由记录里有 `skipped` 和原因；所有者遇到同样的故障时正常切到备用模型。
- 身份未确认的请求被拒绝，上游收到 0 个请求。
- 修复前，成员拿到了受限备用模型的回答。

## 3. 助手的工具白名单和知识范围（P1）

**问题**：创建会话时只应用了助手的模型和 instructions，`tools` 没有生效。`tools: []` 的助手仍有 32 个工具。

**修复**：

- 创建会话时把 `assistant.tools` 映射为 pi-durable 的 `tools`，即会话启用的工具集合。规则如下：
  - 未配置：使用产品默认工具；
  - `[]`：没有任何工具；
  - 列表：只启用列出的工具；如果助手配了团队成员，会自动加上 `delegate`。
- 这个集合既决定模型能看到哪些工具，也决定嵌套调用（`callable`，Code Mode）能调用到哪些，所以不只是隐藏了工具描述。
- 助手的知识范围写入会话的 `wr.assistant` 文档，`kb_search` 和知识范围提示与子代理成员一样受它限制。

**测试**：`r13-identity` 第 3 项。
- `tools: []`：可见工具和可调用工具都是 0，模型请求的工具不会执行；
- 只列出 `wr_fixture_echo`：只有这一个工具；
- 未配置：使用默认工具集；
- 知识范围生效。

## 4. 审批等待（P1）——在 1.5.0 范围内的做法

**限制**：
- 1.5.0 中，每次崩溃时工具调用如果处于“运行中”，都会累加 `restarts`。工具调用没有自己的检查点，也不能主动挂起；`ToolPark` / `defineSignal` 还在 Unreleased 里。
- 所以等待只要留在工具调用内，就一定会被计数。我们没有关闭重启次数限制。

**做法**（`server/src/runtime/effects.ts`）：

- 每条审批记录绑定等待它的 `taskId`。
- 这次调用被中断达到 `PARK_AFTER_RESTARTS` 次（默认为重启上限减 2，即 3 次）时：
  - 把等待交给独立的持久任务 `wr.approval-watch`。它每 2 秒用 `sleepUntil` 加检查点轮询一次审批状态；睡眠算作进展，崩溃次数不会累加到上限。
  - 原调用立即结束，什么也不执行，并明确告诉模型“正在等待审批”。
- 用户做出决定后，监视任务把结果作为一条后续消息“[审批结果] …”发回会话，请求 id 由任务 id 派生，重启后也不会重复。
- 模型随后用相同参数重新调用。按请求指纹匹配到已有的决定，只消费一次，不会再问一遍。

**仍有的差距**：
- 前 2 次崩溃仍在调用内等待，会计入重启次数。
- 转交之后，由模型重新调用来接着做，不是原调用原地继续。
- 等升级到带 park/signal 的版本，再改为原生挂起和唤醒。

**测试**：`server/test/r13-approval-lifecycle.test.ts`。
- 子进程服务器在审批等待期间被 SIGKILL 7 次。工具没有因 `restart_limit` 终止（修复前在第 5 次被终止），审批仍可处理；批准后重新调用一次完成，不会再次询问。

## 5. 旧租约下的自动恢复（P1）

**修复**（`server/src/runtime/harness-manager.ts`）：

- **到期重试**：启动时因他人租约未过期而跳过的空间，在租约到期时重试，加指数退避和最多 50% 的抖动；每个空间最多 6 次，`stop()` 时取消。
- **周期巡检**：默认每 30 秒一次（`WORKROOM_RT_RESUME_SWEEP_MS`），处理三件事：
  - 打开“调度索引显示有待运行任务、但本进程没有 Harness”的空间；
  - 补写之前写失败的调度索引；
  - 重新挂上丢失的唤醒定时器。
- **调度索引写失败**：在空间目录下写一个 `.wake-mirror-dirty` 标记。选空间目录，是因为它与业务库不在同一个存储，业务库写失败时它通常仍可写。下次启动时扫描这些标记并恢复对应空间。

**测试**：`server/test/r13-lease-resume.test.ts`，5 项。审查描述的场景：启动时他人租约还有约 1 秒，租约过期后空间自动打开，待运行的任务完成，期间没有任何新请求。

**仍有的差距**：如果在持久提交之后、第一次写调度索引之前崩溃，不会留下标记。要覆盖这种情况，只能启动时打开所有空间，所以没有做。

## 6. 停止父任务后的收尾（P2）

**修复**（`server/src/runtime/lifecycle.ts`，以及 `service.ts` 的 `abort`）：

- `closeDeadWork` 遍历当前会话及其所有委派子会话，处理两类记录：
  - 运行中的委派，如果承载它的任务已经结束（前台委派是工具调用，后台委派是汇报任务），标记为 `aborted`；
  - 待处理的审批，如果它绑定的任务已结束，标记为已取消。
- 普通“停止”保留后台任务；“全部停止”（`background`）连后台任务一起停。
- 停止接口返回的 `cancelledApprovals` 包含子会话里被取消的审批。
- 对已结束的调用做审批会被拒绝：返回 409 `approval_task_ended`，说明“这一步没有执行”。
- 读取会话状态和处理审批时也会执行同样的对账。

**测试**：
- 前台委派：子会话请求审批后停止父任务，返回 `cancelledApprovals: 1`，委派变为 `aborted`，子会话的审批被取消，再处理它返回 409；
- 后台委派：普通停止和全部停止的处理范围不同；
- 遗留的待处理审批会被关闭。

**仍有的差距**：没有在启动时主动扫描，恢复后第一次读取状态时才会对账。

## 7. 后台任务的任务 id（P1，代码级风险）

**修复**（`server/src/tools/jobs.ts`）：

- “创建后台任务”和“记录 job → task 映射”放进同一个 `api.commit`，映射存在会话文档 `wr.jobs.tasks` 里。
- 重放 `job_start` 时会找到已有的任务，不会再建第二个。
- `tool_jobs.task_id` 只作为可重建的投影使用。
- 任务开始执行前，会核对映射里记录的是不是自己。

**测试**：`server/test/r13-job-atomic.test.ts`。在提交之后、写投影之前停机，清空投影后重开同一数据目录，重放同一个调用：仍只有一个任务，投影也被重建。这是优雅停机加重放的模拟，不是 SIGKILL。
