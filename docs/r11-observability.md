# 第 11 轮 R6：沙箱可观测（生命周期统计 + 预热调阈值）

目的：用自己的数据回答“沙箱多久冷启动一次、多慢、空闲暂停多少次、花多少钱、预热阈值设得对不对”。所有数字都是对已记录事实的只读聚合，没有估算，也没有写死的厂商指标。

代码：`server/src/tools/sandbox/lifecycle-stats.ts`（聚合）、`lifecycle-stats-routes.ts`（接口）；DTO `shared/sandbox-stats.ts`；页面 `web/src/features/stats/SandboxStats.tsx`（统计页「沙箱」区块，挂在 `Dashboard.tsx` 一行）；单价设置 `web/src/features/admin/SandboxPrices.tsx`（挂在 `AdminPage.tsx` 沙箱标签页一行）。

## 2. 指标定义与公式

统一约定：时间范围 `[from, to)` 按事件的 `at`；组织隔离（每个查询带 `org_id`）；没有数据的值是 `null`，页面显示 “—”，不显示 0。

| 指标 | 定义 |
|---|---|
| 创建次数 | `kind = create` 事件数；按触发拆分：`exec`（首次执行兜底）/ `prewarm`（意图预热）/ `explicit`（用户点准备） |
| 创建失败 | `kind = create_failed` |
| 冷启动 P50 / P95 | `create` 事件的 `duration_ms`（`create()` + 就绪）。**不含** `create_failed`；含所有触发（预热的冷启动用户并不等待，但它是真实的启动成本） |
| 恢复次数 / P50 / P95 / 失败 | `resume` 事件 / 其 `duration_ms` / `resume_failed`。厂商自己的隐式恢复（失联后 connect）不产生事件，不在内 |
| 空闲暂停 | `kind = pause` 且 `trigger = idle` |
| 归档 / 销毁 | `archive` / `destroy` 事件数 |
| 运行时长 | 已结束的运行区间 + 仍在运行的区间（下） |
| 估算成本 | 运行小时数 × 管理员设置的单价（下） |
| 代码运行 本地 / 云端 / 升级 | 区间内 `code_run` 调用记录，`status = ok`（工具返回了报告）；升级是云端的子集 |

**分位数：最近秩（nearest-rank）**。升序 x[0..n-1]，`P(p) = x[ceil(p/100 × n) − 1]`（下限 1、上限 n）。n = 0 → `null`；n = 1 → 两个分位都等于这唯一的值（页面小字显示 `n=…`，样本少时别下结论）。例：n=4 的 [10,20,30,40] 给出 P50 = 20、P95 = 40；1…100 给出 50 / 95。

**运行时长**：暂停 / 销毁事件的 `running_ms` 是“自上次创建/恢复起运行了多久”，在**区间结束的那一刻**记账：一个区间算在它结束所在的统计范围内（跨范围边界的区间整段算在结束的范围）。仍在运行的沙箱（实例表 `ready` / `pausing`）从 `running_since`（缺省 `created_at`）算到现在，**仅当“现在”落在所选范围内时计入**（页面上写作“其中运行中”）；过去的范围不含它们（它们还没结束）。暂停中的沙箱不计入（暂停期间不计费）。已知偏差：沙箱丢失（`lost`）而没有 destroy 事件时，该区间不被计入（少算，不会多算）。

**估算成本** = Σ 提供方（运行毫秒 / 3 600 000 × 单价）。单价是组织设置（管理后台 › 沙箱 › 沙箱单价，每个提供方一个数字，单位 **USD/小时**，与统计页费用同币种）。**未设置单价就没有成本**：该提供方成本为 `null`，页面不显示成本卡、表格里显示 “—”；不会用任何默认价。只有部分提供方有单价时，总成本只含有单价的提供方，`costComplete = false`，成本卡标注“部分”；每个有运行时长的提供方都有单价时 `costComplete = true`。单价 0 是有效价格（成本 0）；清空输入框 = 删除单价。

## 3. 预热调优

数据：预热日志（只记“本来可以预热”的决策，每条消息一行）。精度 / 召回的口径沿用 `prewarmStats`（`prewarm.ts`，本轮只给它加了两个可选参数：`untilIso`、`thresholds`，不复制逻辑）：

- 只看 `fired` 与 `below` 两类决策（过阈值但沙箱已就绪 / 已在准备 / 并发上限 / 刚失败过的，对阈值没有信息）。
- **精度** = 发起且之后有 exec 的 / 发起的。
- **召回（估计）** = 发起且有 exec 的 /（发起且有 exec 的 + 低于阈值却之后有 exec 的）。
- **what-if 表**：对阈值 0.1 … 0.9（步长 0.1），用日志里记下的**分数**重算：`tp` = 分数 ≥ t 且之后有 exec，`fp` = 分数 ≥ t 且没有，`fn` = 分数 < t 且之后有 exec；精度 = tp/(tp+fp)，召回 = tp/(tp+fn)。当前阈值那一列与上面的实际精度/召回相等（测试断言）。
- **浪费的预热**：发起的预热，其沙箱（同会话下一个 `trigger = prewarm` 的 create / resume 事件）在**被任何 exec 用到之前**就被暂停或销毁了。判定：`used_at` 为空，或 `used_at` 晚于那次暂停/销毁事件（暂停之后的 exec 会走恢复，救不回这次预热）。`wastedRunningMs` = 这些预热的结束事件的 `running_ms`（它们白白运行了多久，可乘单价得到浪费的金额）。仍在运行且未被用到的是“待定”（不算浪费）；启动失败的预热没有沙箱，两者都不算。
- 预热块是**组织级**，不受 `provider` 筛选影响（日志没有提供方列）。

### 怎么用 what-if 表调阈值

1. 先看样本量：决策数 / 已发起太少（几十条以内）不要调；召回只统计到后来真的执行过的会话，是估计。
2. 看“浪费的预热”和它的运行时长：高 → 阈值偏低（空闲沙箱太多，成本高）；对照估算成本判断值不值。
3. 看召回：低 → 很多会话仍要冷启动（对照“冷启动 P95”与“创建次数”里 `按需` 的占比）；`按需` 占比高说明预热没拦住。
4. 在表里找精度可接受（例如 ≥ 70%）里召回最高的阈值；本轮默认值 30% 来自手写数据集，不是线上标定（`docs/r11-prewarm.md` §4）。
5. 在管理后台 › 沙箱改“触发阈值 %”（或 `PUT /api/sandbox/prewarm { threshold }`），过一两周再看同一张表，确认冷启动 P95、浪费预热、成本三项的变化。
6. 想知道是哪些特征在误报 / 漏报：用 `docs/r11-prewarm.md` §6 的两条 SQL。

## 7. 没有做 / 没有验证

- 种入的事件只证明聚合与页面正确，**不是真实流量**；真实的冷启动 / 恢复数字取决于提供方。LIVE 段只在本机 OpenSandbox（Docker）上跑，E2B / Daytona 的事件来自同一个 RemoteDriver 代码路径，但没有对真实服务验证（无密钥）。
- 成本是“运行小时 × 你填的单价”的估算：不读取厂商账单，不含存储 / 流量 / 归档费用；单价币种固定为 USD 标签。
- 没有预聚合：聚合在请求时对范围内的事件逐行计算（事件量按会话计，普通规模毫秒级）；非常大的组织需要预聚合或限制范围。
- 厂商自己暂停 / 恢复（Workroom 失联时）不产生事件，所以不会进入恢复统计与运行时长；`lost` 沙箱的未闭合区间少算。
- 召回是估计（见 §3）；预热块不能按提供方筛选。
- 会话级接口没有界面入口；统计页没有按会话的下钻表（接口返回运行时长前 20 的会话，界面暂未展示）。
