# Round 10 · 停止 与 继续

用户反馈（原话）：「这个会话如果被暂停了，为什么直接将最近一轮用户的输入都给他剔除，这个好不友好呀，这个和 deepagents 的 checkpointer 差距好大，我感觉是不是你的实现问题哦」。
截图里：消息「你帮我随意改一下我在做测试」已被应用，助手跑了 5 步，用户点了停止，那条消息下面写着「这条消息没有得到回复：未应用（已被取消）」；用户只好再输入「继续」。

## 1. 结论：丢了什么，只是标错了什么

用真实服务端 + 测试模型（fixture）复现（`server/test/round10-stop.test.ts`，每一条都是对模型的**真实请求**断言，不是看回答推断）：

| 项 | 停止之后 | 结论 |
| --- | --- | --- |
| 用户这条输入 | 仍在 pi-durable 的上下文里（`pi.user`/`wr.input` 条目），下一次模型请求原样带上 | **没有丢**，只是标签错了 |
| 已完成的步骤和工具结果 | 条目、结果都在，下一次请求带上 | **没有丢** |
| 被停止截断的那一步 | pi-durable 给它写一条 `Tool x was aborted` 错误结果；下一次请求带上它 | 没丢，但界面把它标成「失败」（现改为「已停止」） |
| 停止时模型还在思考（还没有任何步骤） | 用户输入在上下文里，没有 assistant 条目 | 没丢 |
| 提交记录（submission） | pi-durable 把这次运行的输入记为 `unanswered`、原因 `aborted`，**但它有 `entry`（已放入对话）** | 这就是「未应用」的来源：`unanswered` 被翻译成「未应用」，而它其实已应用 |
| 停止时还在**排队**的后续消息 | pi-durable 的 `abort()` 语义：撤回所有排队输入（**不是我们实现的问题**）。它们没有进入上下文 | 此前只留一个「未送达」标记，内容不会回到输入框 → 现改为回到输入框 |
| 停止时正在等待的审批 | 审批记录仍是 `pending`，卡片还能点「允许」，但对应的工具调用已被 abort | **我们的实现问题**，已修：停止时置为 `cancelled` |
| 停止时正在发送的外部写入（`dispatching`） | 工具被 abort 来不及记录结果，状态卡在 `dispatching`，界面没有「待核对」 | **我们的实现问题**，已修：停止时转为 `needs_reconciliation`（待核对） |
| 「继续」按钮 | 早就有（运行条，`POST …/continue`），但文案是「已取消 · 已被取消」，没有说明保留了什么；用户没有认出它是真正的续跑 | 现改为「已停止 · 已完成 N 步」+ 说明 |

用户输入的「继续」：作为一条**新的用户消息**，模型看到的是 `[原输入, 工具调用, 已完成结果, 被截断结果, "继续"]`（测试 3 断言）。所以它「能用」，但多了一条消息、也依赖模型把「继续」理解对；真正的继续（`POST …/continue`）不新增消息，直接从存储的上下文再请求一次模型。

## 2. 语义（以 pi-durable 1.5.0 为准）

- **停止** = `conversation.abort()`：结束当前运行的所有任务；**排队中的输入被撤回**（队列里的写入保留）。已经放入上下文的一切保持不变。
- **继续** = `submit({type:"continue"})`（`POST /conversations/:space/:id/continue`）：在**现有上下文**上开一次新运行，让模型回答上次停下时留下的用户消息或工具结果。
  - 忙时抛 `ConversationBusy`（HTTP 409 `busy`，从不排队）。
  - 上下文以回答结尾（没有可继续的内容）→ 运行以 `nothing_to_answer` 结束，不发请求（来自 pi-durable 文档，未单独测试）。
  - 上次失败遗留的排队输入会先于它被放入并加入这次运行。
  - 每次运行的轮数预算（`maxTurns`）从 0 重新计。
- **被截断的工具不会自动重做。**
  - 停止：模型收到 `Tool x was aborted` 错误结果，由模型决定要不要再调用一次（新的调用会重新走审批/外部写入协议）。
  - 进程崩溃：`replay: "safe"` 的工具在重启后自动重跑；`replay: "unsafe"`（沙箱、凭据请求、技能脚本、浏览器会话等）**不会**重跑，模型收到 `interrupted` 错误结果。
  - 外部写入（`wr_fixture_effect` 这类走 effects 协议的）：停止时记为「待核对」，续跑**不会**再执行一次（测试 6 用计数文件断言只执行了 1 次）；模型若用同一个 key 再试，也只会得到「待核对」，不会盲目重发。
- 「已停止」这条输入的 submission 在 pi-durable 里永远是 `unanswered/aborted`，即使之后「继续」得到了回答也不会改写。界面据此显示：之后已有回答 → 「这一轮中途停止过，之后已继续完成」（灰色），否则 → 「已停止（已完成 N 步）」。

## 3. 用户看到什么

- 用户消息下面：`已停止（已完成 N 步）· 这条消息和已完成的步骤都保留在对话里`（灰色，不是红色错误）。N 为这条消息之后成功完成的工具步骤数；还没有步骤时写「还没有完成的步骤」。
- 步骤链：`已停止 · 已完成 N 步 · 1 步被中途截断，没有重做`；展开后被截断的那一步标「已停止」（不是「失败」），并说明不会自动重做。继续并得到回答后变为 `已完成 N 步 · 1 步被中途截断，没有重做`。
- 输入框上方的运行条：`已停止 · 已完成 N 步` + 「继续」按钮（真实调用 continue）+ 「说明」（保留了什么、继续会做什么、被截断的那一步不会自动重做）。失败/超时/中断时同一位置是「重试」（同一个 continue 路由）。
- 只有**从未进入对话**的输入才写「未送达模型：这条消息没有进入对话，模型没有看到它」。停止时还在排队的消息：内容和附件**自动放回输入框**（已有草稿时接在前面），并有一条提示；标记上还有「放回输入框」按钮（刷新、换设备之后也能用）。
- 停止时正在等审批：卡片消失，步骤显示「已停止 / 已取消」，不会留下一个点了也没用的「允许」。
- 停止时正在写外部系统：出现「待核对」卡片，由用户确认是否已生效。

## 4. 与 LangGraph / deepagents checkpointer 的对比

（LangGraph 一侧是对其公开文档的理解，本仓库里没有运行它，请当作概念对照而不是逐项验证。）

相同之处：
- 都是「状态持久化在存储里，续跑 = 从最近的检查点接着来」：用户输入、已完成的步骤/工具结果都不会因为中断而消失；线程（thread / conversation）可以随时用同一个 id 继续。
- 都支持从历史某一点分叉（LangGraph time-travel / 本产品的「编辑（新分支）」「从这里分叉」「重新生成」）。
- 都支持「等待人确认」的中断点，决定之后继续（interrupt/resume ↔ 审批卡片）。

不同之处：
- **检查点粒度**：LangGraph 在每个 super-step 结束时存检查点；pi-durable 存的是任务级的状态机（每个模型请求、每个工具调用各自是一个可恢复的任务）+ 条目日志。结果上，两边「输入 + 已完成步骤」都保留；半途的**模型输出**两边都不保留部分内容（本次只用 fixture 验证了「模型还没开始输出时被停止」这一种，真实流式中途停止时部分文本是否保留未验证）。
- **被打断的那一步怎么办**：LangGraph 恢复时会**重新执行**被打断的节点（至少一次，要求节点幂等）；pi-durable 的**停止**不重跑：模型看到「已中止」错误结果，自己决定；**崩溃**时只重跑声明为 `safe` 的工具。我们对「会产生外部影响」的工具更保守（待核对，不自动重发）。这是有意的差异，代价是续跑后模型可能需要再发一次调用。
- **停止 vs 中断**：LangGraph 的 interrupt 是图里显式的暂停点；这里的「停止」是用户随时取消，等价于取消正在跑的 task 后用「继续」恢复。
- **排队消息**：LangGraph 没有「运行中排队」的概念（新输入要等本次调用结束或开新调用）；pi-durable 有 steer / follow-up 队列，停止时队列被撤回——这是它的语义，我们的补偿是把这些消息还给输入框。
- **审批/外部写入的账本**是我们自己的文档（`wr.approvals` / `wr.effects`），不是 pi-durable 的功能；停止时它们要和 abort 一起收尾（本轮修复的就是这里）。

没有等价物 / 做不到的：
- 「从被打断的那一个工具调用的**中途**接着执行」：停止是取消，不是暂停；被取消的工具不会从中途恢复。
- 在运行中途「暂停」后原地继续同一次工具执行：不支持。
